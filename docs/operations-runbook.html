Overview & architecture

This repository is a monorepo with three deployable concerns:

  • frontend/ — Next.js 14 (App Router), TypeScript, Tailwind. Serves the public website, the Admin console, and the HR ATS portal.
  • backend/ — FastAPI + SQLAlchemy 2 + PostgreSQL, Alembic migrations, an optional ARQ background worker, Redis for cache/queue.
  • deploy/ — Nginx, systemd units, logrotate and the daily pg_backup.sh for the bare-metal production host.

There are two supported production shapes; pick one and stick with it:

A · Docker Compose DOCKER

One file (docker-compose.prod.yml) brings up Postgres, Redis, the backend (gunicorn), the frontend (next start) and an Nginx container that terminates TLS. Easiest to reproduce.

B · systemd + Nginx SYSTEMD

The app runs as native systemd services (pugweb-backend, pugweb-frontend) behind the host's Nginx. This is what deploy/ and docs/deployment-guide.md describe for the shared EC2 host (parisunitedgroup.com).

ℹ︎Throughout this doc, replace pug_user / pug_holding with your actual values from backend/.env if you changed them. Production hostnames assume parisunitedgroup.com — change to match your domain.

Local · Docker (recommended) LOCALDOCKER

One command boots the whole stack with hot-reload on both apps. The backend runs alembic upgrade head automatically on every start.

1One-time: create env files

cp backend/.env.example backend/.env
cp frontend/.env.example frontend/.env.local

What: seeds the two env files. The compose file supplies sensible dev defaults (DB creds, SECRET_KEY), so you can leave everything blank and it still boots. Fill in AI_*, SMTP_*, R2_* only when you need those features.

2Build the images (first time / after Dockerfile or dependency changes)

docker compose build

What: builds the backend & frontend images. First build takes a few minutes; later builds reuse cached pip/npm layers.

3Bring the stack up

docker compose up -d            # start postgres + redis + backend + frontend
docker compose ps               # confirm every service is healthy
docker compose logs -f backend  # tail the backend log (Ctrl-C to stop tailing)

When healthy: Frontend → localhost:3000 · API docs → localhost:8000/docs · Postgres → localhost:5432 (pug_user / pug_password / pug_holding).

4Seed baseline data (first time)

docker compose exec backend python -m app.scripts.seed_users   # roles, permissions, admin users
docker compose exec backend python -m app.scripts.seed_cms     # hero slides, companies, news, settings
docker compose exec backend python -m app.scripts.seed_hr      # HR roles + sample job openings

What: idempotent seeders — safe to re-run; they update roles/content but never overwrite a user's password. Default seed login: superadmin@pug.example.com / ChangeMe!123 (change immediately outside dev).

Optional: background worker (ARQ)

docker compose --profile worker up -d worker

What: the worker is behind a compose profile, so a plain up doesn't start it. Use this when testing queued jobs (embeddings, bulk processing).

Stop / tear down

docker compose down       # stop & remove containers — KEEPS postgres/redis data
docker compose down -v    # also DELETE the volumes (fresh empty DB next boot)
⚠down -v is destructive. It drops the postgres_data and redis_data volumes — every local row is gone. Use plain down for a normal stop.

Local · Manual (venv + npm, no Docker) LOCAL

Use this if you'd rather run Postgres natively and the apps directly on your machine.

1Create the database

sudo -u postgres psql -c "CREATE USER pug_user WITH PASSWORD 'pug_password';"
sudo -u postgres psql -c "CREATE DATABASE pug_holding OWNER pug_user;"
sudo -u postgres psql -c "GRANT ALL PRIVILEGES ON DATABASE pug_holding TO pug_user;"

What: creates the role + database that match backend/.env.example. Adjust the password and keep it in sync with your .env.

2Backend — venv, install, migrate, seed, run

cd backend
python -m venv .venv
source .venv/bin/activate            # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env                 # then edit DB creds / SECRET_KEY if needed

.venv/bin/alembic upgrade head       # create/upgrade all tables
python -m app.scripts.seed_users
python -m app.scripts.seed_cms
python -m app.scripts.seed_hr

python run.py                        # serves on http://localhost:8000

Alternative run command (explicit host/port, e.g. to expose on your LAN):

uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload

3Frontend — install & run (separate terminal)

cd frontend
npm install
cp .env.example .env.local           # set NEXT_PUBLIC_API_BASE_URL if backend isn't on :8000
npm run dev                          # http://localhost:3000  (binds 0.0.0.0)

Verify

cd backend && pytest -q            # backend tests
cd frontend && npm run type-check  # TS strict check
cd frontend && npm run lint         # eslint

Local · Common operations LOCALDOCKER

Migrations

docker compose exec backend alembic upgrade head                       # apply pending migrations
docker compose exec backend alembic revision --autogenerate -m "describe change"  # create a new one
docker compose exec backend alembic current                            # show current revision
docker compose exec backend alembic history                            # full migration history
ℹ︎Migrations run automatically on every docker compose up, so pulling a branch with new migrations and re-running up -d is usually enough.

docker compose exec backend bash                               # shell inside the backend container

Tests & checks

docker compose exec frontend npm run type-check   # frontend TypeScript
docker compose exec frontend npm run lint         # frontend lint

Production · Docker Compose PRODUCTIONDOCKER

Uses docker-compose.prod.yml — production Dockerfile targets, gunicorn with workers, no source bind-mounts, Postgres/Redis with no host ports, and an Nginx container terminating TLS.

1One-time pre-flight on the host

a) Generate a strong SECRET_KEY and put it in backend/.env:

python3 -c "import secrets; print(secrets.token_urlsafe(64))"

b) backend/.env must contain at minimum:

SECRET_KEY=<the value generated above>
POSTGRES_USER=pug_user
POSTGRES_PASSWORD=<strong-random-password>
POSTGRES_DB=pug_holding
PUBLIC_SITE_URL=https://parisunitedgroup.com
CORS_ORIGINS=https://parisunitedgroup.com,https://www.parisunitedgroup.com
# plus R2_*, AZURE_OPENAI_* / AI_*, SENTRY_DSN_BACKEND as you use them

c) frontend/.env.local must contain:

NEXT_PUBLIC_API_BASE_URL=https://parisunitedgroup.com/api/v1

d) Drop the Cloudflare Origin Certificate into deploy/docker/tls/ as origin.crt + origin.key, then lock down the key:

chmod 600 deploy/docker/tls/origin.key
⚠Never commit backend/.env, frontend/.env.local, or the TLS key. They are host-only secrets.

2Bring it up

docker compose -f docker-compose.prod.yml up -d --build

What: builds the production images and starts Postgres, Redis, backend (gunicorn, 4 workers), frontend (next start) and Nginx (ports 80/443). The backend runs alembic upgrade head before gunicorn boots.

Optional: background worker

docker compose -f docker-compose.prod.yml --profile worker up -d

Logs / stop

docker compose -f docker-compose.prod.yml logs -f          # all services
docker compose -f docker-compose.prod.yml logs -f backend  # just the API
docker compose -f docker-compose.prod.yml ps               # status + health
docker compose -f docker-compose.prod.yml down             # stop (keeps data)
⚠docker compose -f docker-compose.prod.yml down -v deletes the production database, redis and uploads volumes. Do not run it unless you intend to wipe everything.

Backup PRODUCTION

Two things need backing up: the PostgreSQL database and the uploads directory (local-disk media; R2-backed installs keep media in the bucket already).

A · Database — automated daily dump SYSTEMD

The repo ships deploy/scripts/pg_backup.sh: a pg_dump + gzip with 14-day retention and an optional S3 push. Install it as a cron job:

sudo cp /home/parisgroup/PugWebSite/deploy/scripts/pg_backup.sh /usr/local/bin/pugweb-pg-backup
sudo chmod +x /usr/local/bin/pugweb-pg-backup
sudo install -d -o parisgroup -g parisgroup /var/backups/pug

Add to root's crontab via sudo crontab -e:

# Daily 02:30 UTC PostgreSQL dump + 14-day rotation
30 2 * * * /usr/local/bin/pugweb-pg-backup >> /var/log/pugweb/backup.log 2>&1

What: writes /var/backups/pug/pug_holding-YYYY-MM-DD.sql.gz each night, pruning dumps older than 14 days. To also ship offsite, uncomment the aws s3 cp block in the script and set S3_BUCKET.

Run it on demand

sudo /usr/local/bin/pugweb-pg-backup

B · Database — manual dump SYSTEMD

pg_dump --host=localhost --port=5432 --username=pug_user \
        --no-owner --no-privileges --clean --if-exists \
        pug_holding | gzip --best > pug_holding-$(date -u +%F).sql.gz

What: a self-contained logical backup. --clean --if-exists makes the dump drop & recreate objects on restore, so it restores cleanly into an existing database.

C · Database — Docker Compose stack DOCKER

In production the Postgres container has no host port, so dump through the container. -T disables the pseudo-TTY so the pipe works:

docker compose -f docker-compose.prod.yml exec -T postgres \
  sh -c 'pg_dump -U "$POSTGRES_USER" --no-owner --no-privileges --clean --if-exists "$POSTGRES_DB"' \
  | gzip > pug_holding-$(date -u +%F).sql.gz

What: reads the DB credentials from inside the container's environment, so you never hard-code them. Works the same for local dev — swap -f docker-compose.prod.yml for nothing (local) and the command is identical.

D · Uploads (local-disk media)

systemd host — rsync the uploads tree to a sibling host:

rsync -aH --delete /var/www/pug/uploads/ backup-host:/srv/pug-uploads/

Docker stack — copy the uploads volume out of the backend container:

docker compose -f docker-compose.prod.yml cp backend:/app/uploads ./uploads-$(date -u +%F)

E · Physical volume snapshot (advanced) DOCKER

For a cold, byte-level copy of the Postgres data volume (stop the stack first so the files are consistent):

# confirm the exact volume name first (project name = lowercased repo folder):
docker volume ls | grep postgres_data
# e.g. pugholdingwebsite_postgres_data

docker compose -f docker-compose.prod.yml down
docker run --rm \
  -v pugholdingwebsite_postgres_data:/data:ro \
  -v "$PWD":/backup alpine \
  tar czf /backup/postgres_data-$(date -u +%F).tgz -C /data .
docker compose -f docker-compose.prod.yml up -d
ℹ︎Prefer the logical pg_dump (sections A–C) for routine backups — it's portable across PostgreSQL versions. Use the volume tar only for full-machine snapshots.

Restore PRODUCTION

⚠Restoring overwrites the current database. Take a fresh dump of the live DB first (in case you need to undo the undo), and always stop the API so nothing writes mid-restore.

A · Database — systemd host SYSTEMD

# 1. Stop the API to prevent writes during restore.
sudo systemctl stop pugweb-backend

# 2. Drop & recreate the database.
sudo -u postgres psql -c "DROP DATABASE pug_holding;"
sudo -u postgres psql -c "CREATE DATABASE pug_holding OWNER pug_user;"

# 3. Stream the gzipped dump back in.
gunzip -c /var/backups/pug/pug_holding-<DATE>.sql.gz | sudo -u postgres psql pug_holding

# 4. Bring the API back.
sudo systemctl start pugweb-backend

Replace <DATE> with the dump's date, e.g. 2026-06-01.

B · Database — Docker Compose stack DOCKER

Because the dumps use --clean --if-exists, you don't need to drop the database — just stop the app, pipe the dump into the Postgres container, and restart.

# 1. Stop the app containers (keep postgres running).
docker compose -f docker-compose.prod.yml stop backend worker

# 2. Pipe the gzipped dump into psql inside the postgres container.
gunzip -c pug_holding-<DATE>.sql.gz | \
  docker compose -f docker-compose.prod.yml exec -T postgres \
    sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'

# 3. Start the app again.
docker compose -f docker-compose.prod.yml start backend worker

C · Uploads

systemd host:

rsync -aH backup-host:/srv/pug-uploads/ /var/www/pug/uploads/

Docker stack — copy a saved uploads folder back into the backend container:

docker compose -f docker-compose.prod.yml cp ./uploads-<DATE>/. backend:/app/uploads

D · Verify the restore

# systemd
curl -s http://127.0.0.1:8000/api/v1/health
# docker
docker compose -f docker-compose.prod.yml exec -T postgres \
  sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "\dt"'  # tables should be present
✓Practise a restore on a staging box at least once before you need it for real — an untested backup is not a backup.

Rollback PRODUCTION

systemd SYSTEMD

sudo -iu parisgroup
cd /home/parisgroup/PugWebSite
git log --oneline -5          # find the last-known-good commit
git checkout <good-sha>

# If the bad deploy applied a migration the rollback target lacks:
cd backend
.venv/bin/alembic downgrade <previous-revision>

cd ../frontend && npm run build
exit
sudo systemctl restart pugweb-backend.service pugweb-frontend.service

Docker Compose DOCKER

cd /path/to/PUGHoldingWebSite
git log --oneline -5
git checkout <good-sha>
docker compose -f docker-compose.prod.yml up -d --build

# If a migration must be undone, run it before traffic returns:
docker compose -f docker-compose.prod.yml exec backend alembic downgrade <previous-revision>
⚠Migrations in this project are kept additive (nullable columns, no drops), so a code rollback usually works without a DB downgrade. Only downgrade if a new migration is genuinely incompatible with the older code — and restore from backup if a downgrade isn't safe.

Troubleshooting

SymptomLikely cause / fix
backend keeps restarting — "connection refused"Postgres still warming up. depends_on: service_healthy self-corrects in ~5–10s.
alembic fails on first boot: "relation already exists"Stale volume from a previous run. docker compose down -v then up -d (local only — never on prod data).
Frontend loads but API calls failfrontend/.env.local overrides the compose URL. Set NEXT_PUBLIC_API_BASE_URL to the right origin (local: http://localhost:8000/api/v1).
psycopg2.errors.UndefinedTableMigrations not applied: alembic upgrade head (in the container or venv).
psycopg2 wheel build fails (Windows)You're on Python 3.13/3.14 — recreate the venv with 3.11 or 3.12.
ModuleNotFoundError: appActivate the venv inside backend/ before running.
Login returns 403Account exists but lacks the role scope for that portal (admin vs HR).
PUG Accounts app 502s after a deployYou edited the wrong Nginx file. Restore /etc/nginx/sites-available/pugaccounts from git/backup and reload Nginx.
Uploads disappear after up --buildEnsure UPLOAD_DIR=/app/uploads (set in docker-compose.prod.yml) so writes land on the persistent volume, not an unmounted in-container path.
AI features unavailableSet AI_ENABLED=true and the provider settings (Azure / OpenAI-compatible / Ollama) in backend/.env or in Admin → AI Settings.
